# `dsh-ecc-commands` — 工作模式与提示词示例

**用途：**为当前会话启用或停用三个经过验证的 ECC Commands 的自动选择：build-fix、test-coverage 和 update-docs。此开关仅对用户可用。Research、Analysis 和 Implementation 是后续任务的类型，并非独立的切换命令。

若要启用自动选择，请由用户单独发送一条直接消息：

```text
/dsh-ecc-commands on
```

不要在命令中附加任务。收到确认后，从下方选择一个模板，并在下一条单独消息中发送。若要停用自动选择，请另行发送：

```text
/dsh-ecc-commands off
```

即使关闭了自动选择，仍可显式调用 `/ecc-*`。

在 Research 和 Analysis 阶段，仅当这些命令能在不执行操作的情况下提供帮助时才使用：不要修复构建、创建测试或编辑文档。在 Implementation 阶段，只有当具体任务符合经过验证的 `build-fix`、`test-coverage` 或 `update-docs` 时才使用 Command；若不符合，不要强行套用 Command。

## 🔍 研究 (Research)

了解现有的本地构建、测试和文档流程；不要运行这些流程，也不要进行任何更改。

### 1. 简短

```text
研究项目 <项目路径>：查明构建、测试和文档的组织方式，并指出本地命令及权威信息来源。不要运行或修改任何内容。
```

### 2. 常规模板

```text
研究项目 <项目路径> 中构建、测试和文档的组织方式。

查找相关脚本和配置、测试目录以及权威信息来源文档。说明有哪些检查，以及在哪里描述其结果。提供准确路径；不要仅凭命令名称就认定它可以安全运行。

只读操作：不要运行构建或测试命令、创建文件、安装依赖或访问网络。最后列出信息缺口和待确认的问题。
```

### 3. 详细分步

```text
以只读模式研究项目 <项目路径> 的工程流程；暂时没有具体的修复任务。

1. 阅读本地指引，确定所用的构建、类型检查、测试和文档系统。
2. 追踪 package.json 脚本和配置中的命令与代码、测试及生成文件之间的关系。
3. 查找描述命令、行为和公共接口的权威信息来源，并与文档进行对照。
4. 检查哪些操作可能会修改文件、需要网络或安装依赖——只分析内容，不要运行这些操作。
5. 区分已确认的事实与推测，并列出尚未核实的范围。

不要编辑文件，也不要运行构建、测试、生成器或安装命令。提供包含准确路径和待解答问题的流程图；在收到单独请求前，不要提出修复方案。
```

## 🧠 分析 (Analysis)

评估现有构建、测试和文档的质量与不足。此阶段只做诊断和建议，不进行修复、生成测试或更新文档。

### 1. 简短

```text
分析项目 <项目路径> 的构建、测试和文档：找出已证实的问题和最有价值的改进，并排列优先级。不要运行或更改任何内容。
```

### 2. 常规模板

```text
分析项目 <项目路径> 的现有构建和测试流程及文档，判断它们是否符合代码和项目需求。

找出已证实的错误、有风险的步骤、测试覆盖缺口和过时指引。对每项说明证据、影响、优先级、复杂度和可能的验证方式。另行标注假设。

仅进行只读分析：不要修复构建、创建测试、更新文档或运行有副作用的命令。提出后续步骤选项，由我决定。
```

### 3. 详细分步

```text
对项目 <项目路径> 的构建、测试和文档进行分析性评估；不要修复任何内容。

1. 将构建和测试场景与配置及软件包结构进行对照。
2. 评估现有测试是否覆盖关键场景和错误；用具体模块和测试证明覆盖缺口。
3. 找出与 package.json 脚本、配置、架构、路由或导出项不一致的文档。
4. 对每项问题说明准确证据、风险、影响、优先级和安全的验证方式。
5. 区分紧急缺陷、改进建议以及需要项目负责人决定的问题。

不要运行构建、测试、生成器或外部命令；不要创建测试、修改文档、安装软件包或使用网络。最终提供有依据的讨论选项列表，而不是已经准备好的 diff。
```

## 🛠️ 实现 (Implementation)

用于适合三个经过验证的 Commands 之一的具体任务。执行修复操作前，先商定修改范围和限制。

### 1. 简短

```text
在项目 <项目路径> 中执行 <适用于 build-fix、test-coverage 或 update-docs 的具体任务>。先说明计划并等待确认。只使用本地已有工具；不要安装依赖或访问网络。
```

### 2. 常规模板

```text
需要在项目 <项目路径> 中执行 <具体任务>。此任务属于 <build-fix | test-coverage | update-docs>。

先检查相关源文件、本地指引和验收标准。列出计划使用的文件和命令、预期更改及风险；在我确认前不要运行或编辑任何内容。

确认后，只在指定范围内工作。使用本地已安装的工具；不要运行 npx 或从网络下载内容，不要安装依赖，也不要修改无关文件。执行已商定的检查并报告结果。
```

### 3. 详细分步

```text
在项目 <项目路径> 中执行已商定的任务 <描述>。

适用的 Command：<build-fix | test-coverage | update-docs>。
所需行为或预期结果：<验收标准>。
限制和允许的范围：<软件包、目录、文件>。

1. 确认任务确实符合所选的经过验证的命令；否则停止并提出其他方案。
2. 研究本地指引、现有脚本、测试、文档及预期副作用。
3. 制定准确的操作计划，并先等待我确认。
4. 确认后，仅执行已商定的范围：最小化构建修复、仅在允许范围内编写测试，或只更新指定文档。
5. 只使用已经安装的工具；不要安装软件包、使用 npx 下载内容或访问网络。对于 update-docs，不要运行项目的文档生成脚本；未经单独许可，不要运行破坏性命令。
6. 检查最终 diff 和已商定的本地检查；说明完成内容以及仍未核实的事项。

如果出现副作用、工具不可用或与验收标准冲突，请暂停并协商下一步。
```
