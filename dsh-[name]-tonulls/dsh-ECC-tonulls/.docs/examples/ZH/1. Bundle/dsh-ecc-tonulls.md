# `dsh-ecc-tonulls` — 工作模式与提示词示例

**用途：**为当前 DSH 会话启用所有已启用 ECC 组件（Agents、Skills 和经过验证的 Commands）的自动选择。此开关仅对用户可用，不会创建单独的代理。命令 `/dsh-ecc-tonulls off` 会关闭全部三组的自动选择。使用总开关后，可通过各自的控件单独启用或停用不同组。

## 使用方法

若要允许自动选择所有组件，请由用户单独发送一条直接消息，内容必须与下方命令完全一致：

```text
/dsh-ecc-tonulls on
```

不要在命令中添加说明或任务：路由器只接受完全匹配的消息。收到确认后，从下方选择**一个**模板，并在下一条消息中发送。若要关闭，请另行发送 `/dsh-ecc-tonulls off`。即使关闭了自动选择，仍可显式调用 `/ecc-*`。

`研究`、`分析`和`实现`是三种任务类型，并非额外的切换命令。如果尚不清楚要实现什么，请先从研究开始，再进行分析；只有选定并商定了具体更改后，才使用实现。

## 🔍 研究 (Research)

了解项目现状：用途、代码、文档、架构和限制。此阶段不要进行更改，也不要替用户决定未来的实现方案。

### 1. 简短

```text
以只读模式研究项目 <项目路径>：说明其用途、结构和主要流程。暂时不要进行任何更改，也不要提出实现方案。
```

### 2. 常规模板

```text
研究项目 <项目路径>；目前还没有具体的更改任务。

1. 阅读本地指引，简要说明项目用途及其主要组成部分。
2. 梳理关键入口点以及主要数据流或控制流。
3. 将代码与 README、文档和现有测试进行对照。
4. 根据仓库中的事实，列出使用的技术、外部依赖和明显限制。

不要进行任何更改，也不要提出实现计划。最后说明已经了解的内容、尚未核查的范围，以及需要向我确认的信息。
```

### 3. 详细分步

```text
研究项目 <项目路径>；目前尚未明确具体任务。

1. 先查找并遵循本地 AGENTS.md、README 及其他项目指引。
2. 绘制目录、关键模块、公共接口和入口点的结构图。
3. 从入口到结果追踪 2–3 个主要用户或系统场景；以代码和测试为依据。
4. 将架构与文档进行对照，并标明已确认的不一致之处。
5. 列出使用的存储、服务、依赖和外部边界；不要凭空推断缺失的信息。

不要编辑文件、安装依赖、运行破坏性命令或访问网络。报告中应区分已确认的事实、假设和未知事项；注明已检查的范围和剩余信息缺口。暂时不要提出具体需要实现的内容。
```

## 🧠 分析 (Analysis)

根据项目现状找出问题、改进机会和想法。分析应以事实为依据，帮助选择方向，但不能取代用户决策，也不能修改项目。

### 1. 简短

```text
分析项目 <项目路径>：找出最有价值的改进机会，用代码或文档示例说明依据并排列优先级。不要进行任何更改。
```

### 2. 常规模板

```text
根据项目 <项目路径>（或范围 <范围路径>）的代码、文档和测试进行分析。

找出已证实的缺陷、技术限制、测试或文档缺口，以及有前景的改进。对每项建议说明证据和涉及范围、预期收益、风险、大致复杂度和优先级。另行标注假设以及需要我决定的问题。

不要修改文件、安装依赖或开始实现。最后简要列出值得进一步讨论的选项。
```

### 3. 详细分步

```text
在尚未预先指定任务的情况下，对项目 <项目路径> 进行分析性审查。目标是找出已证实的问题或良好的改进机会。

1. 根据本地指引和项目实际结构确定审查范围。
2. 研究相关代码、测试、文档和配置；每项结论都要注明依据路径或观察结果。
3. 检查适用于本项目的方面：正确性、可靠性、安全性、性能、可访问性、可维护性和用户场景质量。不要使用不相关的标准。
4. 将实际缺陷、风险、技术债务和新机会分类；不要把假设称为已证实的问题。
5. 评估每项建议的收益、紧迫性、复杂度、风险和依赖项，并按优先级排序。

不要修改文件、运行有副作用的命令、安装软件包或访问网络。最后给出简要总结、值得讨论的重点方向和待解答问题。不要替我选择实现任务。
```

## 🛠️ 实现 (Implementation)

当已有具体需求或选定了分析后的改进方案时使用。先明确验收标准并商定计划；之后才进行有限范围的更改和验证。

### 1. 简短

```text
在项目 <项目路径> 中实现 <具体更改>。先研究本地指引，并提出包含涉及文件和验证步骤的计划；等待我确认。如果需求不明确，请先提问。商定后进行最小范围的更改，并运行相关检查。
```

### 2. 常规模板

```text
需要在项目 <项目路径> 中实现 <具体更改>。

先研究指引、相近实现、测试和文档。制定计划，说明预期行为、涉及文件、验收标准、风险和验证方式。在我确认之前不要进行任何更改。如果需求或验收标准不完整，请先提问。

确认后，只实现已商定的范围，添加或更新相关测试，检查 diff 并运行适当的本地检查。未经单独许可，不要安装依赖、访问网络或执行破坏性操作。
```

### 3. 详细分步

```text
在项目 <项目路径> 中实现已商定的更改。

背景：<已知信息>。
所需行为：<具体场景>。
验收标准：<可验证的结果>。
限制：<兼容性、公共 API、性能、安全性及其他要求>。

阶段 1 — 研究：研究本地指引、现有架构、类似实现、测试以及相关文档。不要猜测未经核实的事实。
阶段 2 — 计划：列出准确的文件、行为变更、测试、风险和可能的替代方案。暂停并等待我确认。
阶段 3 — 实现：确认后，仅修改必要范围；遵循现有约定并保持兼容性。不要添加依赖或修改无关文件。
阶段 4 — 验证：运行相关测试和检查，查看最终 diff，列出结果及剩余限制。

如果需求与项目结构冲突、验收标准无法验证或出现意外影响，请暂停并在继续前协商调整。未经单独许可，不要访问网络或运行破坏性命令。
```
