# `dsh-ecc-agents` — 工作模式与提示词示例

**用途：**为当前会话启用或停用 ECC Agents 角色指令的自动选择。此开关仅对用户可用，不会启动单独的代理。如果尚未明确具体任务，请先从研究开始，再进行分析；确定要实施的更改后再使用实现。这三个标题表示后续请求的类型，并非额外的切换命令。

若要启用自动选择，请由用户单独发送一条直接消息：

```text
/dsh-ecc-agents on
```

不要在命令中附加任务。收到确认后，从下方选择一个模板，并在下一条单独消息中发送。若要停用自动选择，请另行发送：

```text
/dsh-ecc-agents off
```

即使关闭了自动选择，仍可显式调用 `/ecc-*`。

## 🔍 研究 (Research)

了解项目现有代码、架构、角色和工作流程，不替用户决定需要更改什么。

### 1. 简短

```text
以只读模式研究项目 <项目路径>：说明其用途、结构和主要流程。暂时不要进行任何更改，也不要提出实现方案。
```

### 2. 常规模板

```text
研究项目 <项目路径>；目前还没有具体的更改任务。

1. 阅读本地指引，简要说明项目用途及其主要组成部分。
2. 梳理关键入口点、数据流以及主要模块之间的关系。
3. 将代码与文档和测试进行对照；引用作为依据的文件路径。
4. 列出关于架构、技术和限制的事实，并说明哪些方面尚未能核实。

不要修改文件，也暂时不要提出实现计划。区分事实和推测，并在最后提出有助于继续研究的问题。
```

### 3. 详细分步

```text
以只读方式研究项目 <项目路径>；目前尚未明确具体任务。

1. 查找并遵循本地 AGENTS.md、README 及其他指引。
2. 绘制结构图：入口点、主要软件包、公共接口和关键依赖。
3. 从入口到结果追踪若干重要场景，并通过代码和测试进行核实。
4. 研究与架构有关的决策、模块边界及其数据交换方式。
5. 将实际结构与文档对照，并列出已确认的不一致之处。

不要编辑文件、安装依赖、运行破坏性命令或访问网络。报告中应注明已核查的范围、事实的准确来源、未知事项和待解答问题。不要替我决定未来采用哪种实现方式。
```

## 🧠 分析 (Analysis)

基于事实判断项目在哪些方面适合修复或改进。分析不应演变为代码修改，也不应擅自选定任务。

### 1. 简短

```text
分析项目 <项目路径>：找出几项最有价值的改进或已证实的问题，用代码或文档说明依据并排列优先级。不要进行任何更改。
```

### 2. 常规模板

```text
根据代码、测试和文档分析项目 <项目路径>（或范围 <范围路径>）。

找出已证实的缺陷、架构风险、缺口和改进机会。对每项说明证据、涉及的文件、影响、收益、风险、工作量和优先级。区分必须解决的问题与可选建议。

不要修改文件，也不要开始实现。另行列出假设和需要我决定的问题；提出几个后续步骤选项。
```

### 3. 详细分步

```text
在尚未预先指定任务的情况下，对项目 <项目路径> 进行分析性审查。

1. 根据本地指引和项目的实际结构，确定分析范围。
2. 研究相关代码、测试、配置和文档；每项结论都要有具体路径或可核实的观察作为依据。
3. 将发现分为缺陷、风险、技术债务和新机会。不要把假设说成已确认的问题。
4. 评估每项建议的影响、紧迫性、工作量、风险和依赖项，并说明其优先级。
5. 比较可选方案，并指出哪些决定应由用户作出。

以只读方式工作：不要编辑文件、安装依赖或访问网络。最后简要列出可讨论的方向和问题；不要替我选择具体实现方案。
```

## 🛠️ 实现 (Implementation)

用于已经明确具体任务或选定改进方案的情况。先商定范围和计划，再进行实现与验证。

### 1. 简短

```text
在项目 <项目路径> 中实现 <具体更改>。先研究指引，并提出包含文件和验证步骤的计划；等待我确认。如果需求信息不足，请先提问。获得确认后，进行最小范围的更改并验证结果。
```

### 2. 常规模板

```text
需要在项目 <项目路径> 中实现 <具体更改>。

先研究本地规则、相近实现、测试和文档。制定计划，说明预期行为、涉及文件、验收标准、风险和验证方式。在我确认之前不要做任何更改；如果任务有多种解释，请先澄清需求。

确认后，只实现已商定的范围，添加或更新相关测试，并运行适当的本地检查。未经单独许可，不要安装依赖、访问网络或执行破坏性操作。
```

### 3. 详细分步

```text
在项目 <项目路径> 中实现选定的更改。

所需行为：<场景和预期结果>。
验收标准：<可验证的条件>。
限制：<兼容性、API、安全性及其他要求>。

1. 研究本地指引、架构、现有类似实现、测试和文档。
2. 列出准确的文件、可能的实现方案、风险和必要的验证步骤。
3. 暂停并等待我确认计划。确认前不要开始编辑。
4. 确认后，仅进行已商定的最小范围更改，并只更新相关测试或文档。
5. 运行相关检查，检查最终 diff，并说明仍未核实的事项。

如果需求不明确或验收标准无法验证，请先提问。未经单独许可，不要添加依赖、访问网络或运行破坏性命令。
```
