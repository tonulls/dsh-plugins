# `/ecc-code-reviewer` — примеры промтов

## Назначение

Проверяет изменённый код на дефекты качества, безопасности и сопровождаемости. Результат — замечания с доказательствами и приоритетом; ревью не должно незаметно превращаться в исправление.

## 1. Короткий запрос

```text
/ecc-code-reviewer Проведи read-only ревью моих изменений. Сообщи только подтверждённые проблемы с приоритетом и точными местами; код не меняй.
```

## 2. Шаблонный запрос

```text
/ecc-code-reviewer Проверь diff {ветка/коммит/пути} в контексте {цель изменения}. Сосредоточься на корректности, безопасности и сопровождаемости, не повторяй стиль-вкусовщину. Для каждого дефекта укажи серьёзность, файл/строки, сценарий проявления и обоснование. Только анализ: файлы не меняй, исправления не применяй.
```

## 3. Подробный запрос

```text
/ecc-code-reviewer Выполни read-only ревью набора изменений {diff/коммит/пути}. Заявленная цель: {цель и требования}; допустимая область: {модули}.

1. Изучи diff вместе с необходимым контекстом вызывающего кода, контрактов и относящихся тестов; не считай сам факт изменения дефектом.
2. Проверь регрессии корректности, границ ввода/вывода, безопасности и поддерживаемости, которые непосредственно следуют из кода. Для каждого подозрения проследи конкретный сценарий.
3. Отделяй подтверждённые находки от вопросов и не включай неподтверждённые предположения как дефекты. Учитывай тесты как свидетельство, но не считай отсутствие теста само по себе ошибкой реализации.
4. Ничего не редактируй и не запускай исправления. Не устанавливай пакеты и не используй сеть; выполняй проверки только если они явно разрешены и безопасны.

Сначала выведи находки в порядке серьёзности: краткий заголовок, уровень, файл и строки, условие воспроизведения, фактическое последствие и предлагаемое направление исправления. Затем — проверенные области и ограничения. Если подтверждённых проблем нет, скажи это явно и укажи пределы ревью.
```
